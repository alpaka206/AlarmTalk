### 후속 리뷰 2건 — 수정/기록, 실행은 릴리스 단계로 보류

- [복수 정상 영수증의 플랜 교체](https://github.com/alpaka206/AlarmTalk/pull/734#discussion_r3996425192):
  실제 누락. 직전 수정은 조회 실패만 교체 차단 조건으로 보았고, 모두 성공한 경우에는
  만료가 늦은 영수증 하나만 새 구독으로 옮겼다. 이제 선택한 영수증 외에 미확인·유효·보류
  증빙이 남으면 교체와 72시간 강제 만료를 거절한다. 기존 구독·그룹·영수증 연결은 보존한다.
  같은 스토어/같은 새 플랜/자동갱신 해제도 예외가 아니다. 다른 증빙이 모두 종료됐거나
  플랜을 교체하지 않는 갱신은 허용한다. 충돌이 지속되면 전환을 계속 거절하며 임의로 승자를 정하지 않는다.
- [Google REVOKED 조회 상태 누락](https://github.com/alpaka206/AlarmTalk/pull/734#discussion_r3996425190):
  공식 API 계약상 오탐. `SUBSCRIPTION_REVOKED`는 RTDN 알림이고 재조회 상태는
  `SUBSCRIPTION_STATE_EXPIRED`다. 이미 존재하는 EXPIRED 종료 경로를 유지하며,
  혼동을 남긴 Play revoke 폴백의 비공식 상태 분기와 주석·테스트 픽스처를 정리했다.
  [공식 근거](https://developer.android.com/google/play/billing/lifecycle/subscriptions#revoke)는
  [수명주기 스펙](../spec/billing-lifecycle.md)에도 남겼다.

재발 방지 사례는 `packages/backend/test/billing-reconciliation.test.ts`에 11건 추가했다:
복수 정상/동일 스토어/동일 새 플랜/보류의 교체 거절 8건, 다른 증빙 종료 후 교체 2건,
교체 없는 갱신 1건. 거절 시 DB 전체 대상 행·그룹·초대 코드·보관 유예와 푸시 무변경,
72시간 경과 후에도 연결 보존을 기대값으로 둔다. **이번 추가분은 실행하지 않았다.**
빌드·테스트·CI와 별도 자체 전체 리뷰는 사용자 지시로 중단했으며, 기존 통과 결과를
이번 후속 수정의 검증 결과로 재사용하지 않는다. 실행 시점 규약은 루트 `CLAUDE.md`에 있다.

### 다음 리뷰 2건 (`69f81ce2` 대상) — 응답/토큰의 동일성 누락

이번 두 건은 직전 복수 영수증 교체 가드의 재발이 아니다. 그보다 앞서 남아 있던
**읽은 응답과 실제 판정한 응답의 차이**, **소유자를 찾은 토큰과 정합화한 토큰의 차이**다.
앞선 수정이 성공 여부와 구독 ID만 전달하면서 그 차이를 놓쳤다.

- [iOS 구매 전 조회와 이전 전체 조회의 경합](https://github.com/alpaka206/AlarmTalk/pull/734#discussion_r3996519411):
  `refreshSubscriptionForPurchase`가 저장 성공한 응답을 직접 반환하고 구매 판단은 그 값을 쓴다.
  성공한 preflight만 별도의 `billingPreflightRevision`을 올려, 이전 전체/조용한 조회가
  구독·plan과 `/auth/me` 콜백을 덮지 못하게 했다. 전체 갱신의 세대·완료 소유권은 그대로여서
  `isRefreshing`이 잠기지 않으며 실패/취소한 preflight는 이전 전체 갱신을 버리지 않는다.
- [Play 교체 토큰의 첫 비활성 RTDN](https://github.com/alpaka206/AlarmTalk/pull/734#discussion_r3996519414):
  `linkedPurchaseToken`으로 얻은 이전 구독을 새 토큰의 연결로 오인하지 않는다. 마지막
  권위 응답의 계정 바인딩·linked 토큰을 확인하고, 쓰기 트랜잭션에서 이전 활성 연결과 새 토큰
  미등록을 재확인한 뒤 실제 결제일과 새 연결을 기록한다. 그 후 새 토큰을 포함해 정합화한다.
  연결 기록 뒤 조회 실패가 나도 재시도/크론이 새 토큰을 보며, 동시 confirm의 기록은 덮지 않는다.
  새 보류 토큰에는 이전 토큰의 해지 예약을 적용하지 않는다.

재발 방지 사례 작성: iOS 3건(이전 전체/조용한 조회와 성공 preflight, 실패 preflight),
백엔드 실제 DB RTDN 8건(남은 기간·보류/복구·진짜 만료·재시도·바인딩 변경·동시 confirm).
기존 iOS preflight 6건도 구매용 응답 반환 경로를 사용하도록 바꿨다.
**작성만 했고 실행하지 않았다.** 빌드·테스트·CI·별도 전체 리뷰는 실행하지 않았으며,
이번 수정에도 이전 검증 수치를 통과 근거로 사용하지 않는다.

## 함께 고친 결함과 중복 제거

- 결제 전 조회·만료 크론·RTDN 종료/보류는 `billing-reconciliation.ts`를 공유한다.
  스토어 I/O는 쓰기 락 밖에서 하고, 구독·영수증이 바뀌었으면 트랜잭션 안에서 거절한다.
- 보류 때 그룹을 보존하고, 회복 때 멤버 권한·기간과 삭제 유예를 같은 트랜잭션으로 복구한다.
  소유자의 유효 구독이 남아 있으면 멤버만 독립적으로 만료시키지 않는다.
- 구독 스냅샷은 `user_plan`·구독·갱신 스토어를 같은 DB 읽기 트랜잭션에서 구성한다.
  양 앱은 오래된 세션/세대의 응답을 버리고, Play는 SDK의 비동기 제품 조회 이후에도 재검사한다.
- Apple 유예 만료는 `gracePeriodExpiresDate`를 사용한다. 알 수 없는 상태/조회 실패는
  종료로 추정하지 않는다. 만료 크론의 기존 72시간 조회 장애 유예는 유지한다.
- 결제일은 Apple `purchaseDate`, Play 최신 성공 주문의 실제 처리 시각을 사용한다.
  연장·유예·중복 전송을 새 결제로 추정하지 않는다. 예약 교체의 아직 소유하지 않은 상품도 배제한다.
- 선물의 실제 구매일을 저장하고, 탈퇴 시 한 구독에 연결된 여러 증빙을 각각 보존한다.
  토큰 없는 기존 Apple 구독의 바인딩 조회도 저장 키인 originalTransactionId를 사용한다.
- 환불 조회 중 같은 체인의 새 갱신이 반영되면 옛 종료 응답으로 현재 구독/그룹을 지우지 않는다.
- JWT 만료/주체 형식과 정확한 만료 경계를 검사한다. 서버 JWT 설정 누락은 401이 아닌 503이며,
  iOS는 인증 토큰 없이 보낸 요청의 401로 현재 세션을 종료하지 않는다.
- Content-Length 누락/조작과 무관하게 실제 바디 스트림에 25 MiB 상한을 적용한다.
  프로필 PATCH의 null/배열/원시 JSON은 500 대신 400으로 거절한다.
- Android 알림 권한 예외 처리를 기존 runCatching과 동일한 명시적 catch로 표현했다.
  울림 예약·시간 계산·재생·로컬 권한 판정의 동작은 바꾸지 않았다.
- 취약한 baseline-browser-mapping, @humanfs/node, Wrangler/Miniflare 간접 의존성을
  기존 호환 범위 내에서 갱신했다. CI에 high 이상 의존성 감사와 Android release lint를 추가했다.

중복된 SQL 큐 기반 Apple 만료/보류 테스트는 실제 마이그레이션을 적용한 독립 파일 SQLite
통합 테스트로 이관했다. 트랜잭션 롤백, 조회 중 갱신/교체, 멤버 독립 구독, 72시간 경계,
반복 알림 방지, RTDN 실제 HTTP 라우트도 검증한다.
