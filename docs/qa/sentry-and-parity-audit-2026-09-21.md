# Sentry 후속 수정·네이티브 정합성·요청 비용 검토

> **상태 갱신**: 1~6절은 수정 전 HEAD를 검토한 기록이다. 이후 사용자의 수정·전체 검증 요청으로
> R1~R6와 추가 발견을 수정했다. 현재 구현·실행 결과·아직 확인하지 못한 것은 **7절**을 따른다.

## 1. 최초 검토의 결론과 범위

**주요 Sentry 수정 방향은 맞지만, 전체 해결·출시 검증 완료로 승인할 상태는 아니다.**
BGTask 진입 격리 수정과 테스트 Sentry 차단은 코드에서 확인했다. 별도로 iOS 매니페스트의
오래된 응답·계정 경계, 백그라운드 토큰 갱신의 메모리 반영, Android 전경 401 반복,
이벤트 수집의 DB 개별 호출 등 후속 수정이 필요하다.

- 검토 기준: `fix/1.2.9-sentry-followups`, `2d1924ed88e5723fd819022662d6122a9a689b25`.
- 범위: 해당 커밋 73개 파일의 변경 내용과 연결된 인증·백그라운드 동기화·음성 캐시·사용 기록·
  알람 생성·서버 DB 호출·CI 경로. 모든 화면·모든 결제 상태·모든 기기를 검증한 전수 인증은 아니다.
- 기준 규칙: `docs/spec/`와 `CLAUDE.md`. 알람 발사는 계속 로컬이어야 한다.
- Sentry 원본 이벤트, 현재 운영 DB, 스토어 배포 바이너리, 원격 브랜치 보호 설정은 조회하지 않았다.
  제보의 건수·사용자 수·발생 시각·배포 후 재발 여부를 독립 검증한 것은 아니다.
- 로컬 Git 참조에서 이 HEAD를 포함하는 브랜치는 작업 브랜치뿐이었다. 원격 fetch 없이 본
  결과이므로 **미배포라고 단정할 수 없고, 배포됐다고 인증할 수도 없다.**
- 전체 빌드·테스트·실기기 검증은 실행하지 않았다. 제보의 테스트 통과 수치는 이번 검토의
  실행 결과가 아니다. 실제 `/events` 라우트를 메모리에서 실행한 DB 호출 계수만 별도로 확인했다.
- 이번 작업은 검토 문서만 추가한다. 아래 결함을 수정했거나 기존 동작 스펙을 변경한 것은 아니다.
- **추가 발견은 이번 커밋이 새로 만들었다는 뜻이 아니다.** 기존 경로까지 확장해 찾은 항목이다.

## 2. 추가 발견 — 우선순위순

### R1. P1 — iOS 매니페스트의 두 저장 경로가 서로의 세대를 모른다

**근거**

- `apps/ios-native/AlarmTalk/StockClipPrefetcher.swift:188`: 응답을 받은 직후 매니페스트를 저장한다.
  `generation`·취소 확인은 뒤쪽 다운로드 루프의 214행에 있어 저장을 보호하지 못한다.
- `apps/ios-native/AlarmTalk/VoiceStudioViewModel.swift:608`: 자체 `manifestRevision`은 있지만
  이 뷰모델의 조회끼리만 보호한다. 별도 프리페처의 저장과 공유하지 않는다.
- `apps/ios-native/AlarmTalk/StockClipManifestStore.swift:38`: 전역 파일에 원자적으로 쓰지만
  응답 세대·소유 계정 검사가 없다. 원자적 파일 교체는 오래된 응답의 덮어쓰기를 막지 않는다.
- `apps/ios-native/AlarmTalk/AudioCacheStore.swift:624`: 이 파일의 주소를 현재 음원 세대로 믿고
  다운로드 응답이 뒤처졌는지 판정한다.

**문제가 되는 순서**

1. 교체 전 프리페처 조회 A가 시작된다.
2. 교체 후 뷰모델 조회 B가 완료되어 새 매니페스트를 저장한다.
3. 늦게 끝난 A가 같은 파일을 옛 매니페스트로 덮는다.
4. 캐시의 최신 여부를 판단하는 기준 자체가 뒤로 간다. 새 음원을 낡았다고 거절하거나,
   받아 둔 옛 음원을 최신이라고 판단할 수 있다.

계정 경계도 같은 문제다. `VoiceStudioViewModel.swift:160`의 정리는 자기 조회 세대만 올리고
파일을 지운다. 앱의 계정 변경 훅(`AlarmTalkApp.swift:304`)은 프리페처를 취소하지 않는다.
그 뒤 앞 계정의 프리페처 응답이 파일을 되살릴 수 있고, 다음 계정의
`loadStockClips`는 소유자 확인 없이 디스크를 먼저 읽는다(`VoiceStudioViewModel.swift:587`).
**앞 계정의 클론 메타데이터가 다음 계정의 캐시에 섞일 가능성**이지, 서버의 음원 접근 인가를
우회했다고 실증한 것은 아니다.

Android에는 이미 대응하는 저장소 전역 티켓·무효화·계정 표식이 있다:
`apps/android-native/app/src/main/java/com/alarmtalk/app/data/StockClipManifestStore.kt:55`와 172행.

**수정 방향**: iOS도 모든 저장 경로가 같은 저장소의 조회 티켓·계정 세대를 사용하게 한다.
검사·파일 게시·소유자 기록을 하나의 직렬화 경계에서 처리하고, 로그아웃은 파일 삭제와
미완료 티켓 무효화를 함께 한다. 읽기도 소유 계정을 검증한다. 단순 `Task.cancel()` 추가로 끝내지 않는다.

**회귀 조건**: 두 writer의 응답 역전, 조회 중 로그아웃→다른 계정 로그인, 파일 삭제 실패,
새 응답 저장 실패 뒤 옛 응답 도착을 각각 시험한다. 운영 발생 여부·실기기 재현은 미확인이다.

### R2. P2, 낮은 subrequest 상한 환경에서는 P1 — HTTP 배치가 DB 배치가 아니다

**근거**: `packages/backend/src/routes/events.ts:138`의 루프가 직접 입력 문구 붙임·해제마다
`await tx.execute(UPDATE ...)`를 따로 호출한다. INSERT만 25건 단위로 묶었다.
트랜잭션으로 감싼다고 이 개별 호출들이 자동으로 한 번의 원격 요청이 되지는 않는다.

실제 라우트를 esbuild로 메모리에 번들링하고 DB만 계수용 대역으로 교체해 Hono 요청을 실행했다.
개인정보 동의 v5, 서로 다른 이벤트 UUID, `manual_message_attached`와 유효한 문구 UUID를 사용했다.

| 한 요청의 이벤트 수 | 라우트 내부 `execute` 호출 | 그중 문구 UPDATE | 대역 DB에서 HTTP 결과 |
| --- | ---: | ---: | --- |
| 1 | 4 | 1 | 200 |
| 25 | 28 | 25 | 200 |
| 50 | 55 | 50 | 200 |
| 100 | **109** | **100** | 200 |

100건은 동의 조회 1 + 기존 이벤트 조회 4 + INSERT 4 + UPDATE 100이다.
인증·동의 미들웨어 및 트랜잭션 시작·종료 비용은 이 숫자에서 제외했다.
**모든 종류의 100건 배치가 109번인 것은 아니다.** 문구 상태를 바꾸는 이벤트가 많은 경우다.
이 진단은 실제 라우트의 호출 수를 확인한 것이며, 운영 DB 부하 시험이나 Workers 실패 재현은 아니다.

저장소 `packages/backend/src/lib/transactions.ts:13`에는 다른 경로에서 발생한
`Too many subrequests` 운영 사고와 batch 사용 이유가 이미 기록돼 있다.
다만 그 주석의 약 50회를 모든 운영 환경에 일반화해서는 안 된다. 확인 시점 공식 문서는
Free 50회, Paid 기본 10,000회로 구분한다. 현재 운영 요금제·별도 설정은 미확인이다.
[Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/#subrequests)

50회 상한이 적용되는 환경에서는 이 입력이 상한을 넘는다. 두 앱 모두 실패한 가장 오래된
배치를 보존하므로 같은 배치를 계속 재전송하는 정체가 생길 수 있다. 상한이 높아도
100회의 직렬 DB 왕복과 쓰기 트랜잭션 점유 비용은 남는다.

**수정 방향**: 이미 제공되는 `DbExecutor.batch`를 트랜잭션 안에서 사용한다.
기존 이벤트 조회 → 신규 INSERT → 문구 상태 반영의 의미와 순서를 유지한다.
소유권 조건, 이벤트 UUID 멱등, 시각 비교, `last_used_at` 의미를 잃지 않아야 한다.
같은 문구의 이벤트를 합치려면 붙임·해제 순서와 동일 시각 규칙부터 테스트로 고정한다.

**회귀 조건**: 100건 문구 이벤트·재전송·서로 뒤섞인 붙임/해제·미래 시각·타인 문구를 포함하고,
결과뿐 아니라 실제 전송 묶음 수에도 상한을 둔다. 클라 배치를 무조건 1건으로 줄이는 해결은 피한다.

### R3. P2 — iOS 백그라운드 갱신은 Keychain과 메모리 세션을 갈라놓는다

- `apps/ios-native/AlarmTalk/BackgroundSyncTask.swift:362`는 `/auth/me` 응답을
  `EntitlementWriter.renewSession`으로 저장한다.
- `apps/ios-native/AlarmTalk/EntitlementWriter.swift:105`는 Keychain과 이용권 스냅샷을 바꾸지만
  `AuthViewModel.session`에는 발행하지 않는다. Keychain 저장에 세션 변경 알림도 없다.
- 이어지는 push는 `RemoteAlarmPushSync.swift:109`, pull은 `RemoteAlarmPullSync.swift:209`에서
  메모리 세션을 읽는다. 이 사이클의 목소리 조회·날씨 조회는 반대로 Keychain을 읽는다.
- `AuthViewModel.swift:436`의 채택 함수는 메모리가 nil일 때만 동작한다.
- 같은 파일 892행의 401 처리기는 메모리 토큰만 비교하고, 1801행에서 Keychain까지 삭제한다.

따라서 갱신이 성공해도 후속 요청은 옛 토큰을 쓸 수 있다. 그 토큰이 만료된 시점의 401은
새로 저장된 유효한 세션까지 지울 수 있다. **갱신 즉시 항상 로그아웃된다는 주장은 아니다.**
옛 토큰이 아직 유효하면 정상 응답이라 감춰지고, 프로세스 재시작·다른 갱신으로 수렴할 수도 있다.

Android는 저장소 갱신 관찰과 저장 토큰까지 확인하는 401 가드가 이미 있다:
`apps/android-native/app/src/main/java/com/alarmtalk/app/ui/main/MainViewModel.kt:211`과 226행.

**수정 방향**: 계정·출처 토큰 CAS를 통과한 갱신을 Keychain과 메모리의 단일 세션 경로로 발행한다.
401 처리도 저장소의 더 새 세션을 고려해야 한다. 무조건 디스크 값을 덮어쓰거나 로그아웃을
되살리지 않도록 계정 전환·명시적 로그아웃 경계는 유지한다.

**회귀 조건**: BG 갱신 후 실제 push/pull의 Authorization이 새 토큰인지 검사하고,
옛 요청의 늦은 401이 새 세션을 지우지 않는지 확인한다. 현재 launch-handler 회귀 테스트만으로는 잡히지 않는다.

### R4. P2 — Android 전경 알람 push에는 첫 401에서 멈추는 규칙이 빠졌다

`apps/android-native/app/src/main/java/com/alarmtalk/app/data/AlarmSyncService.kt:74`는
회차 시작 토큰으로 모든 후보를 순회한다. 151행의 실패 처리는 취소만 다시 던지고
401을 포함한 나머지는 FAILED 기록 후 계속 진행한다.

중앙 인증 처리기가 비동기로 세션을 끊어도 이 루프가 캡처한 토큰을 바꾸거나 루프를 종료시키지는 않는다.
남은 후보가 N개면 거절될 요청을 더 보내고, 시도할 필요가 없던 행들까지 FAILED로 바꿀 수 있다.
**수정된 WorkManager의 무한 재시도가 그대로라는 뜻은 아니다.** 다른 진입점인 전경 push의 잔여 문제다.

iOS에는 이번 수정으로 `RemoteAlarmPushSync.swift:171`의 401 `break`가 들어갔다.

**수정 방향**: Android도 인증 실패면 회차를 멈춘다. 일반 일시 오류의 재시도와 구분하고,
남은 미전송 행은 원래 상태로 보존한다. 재로그인·토큰 교체 후 다시 처리한다.

**회귀 조건**: 후보 3개 중 첫 요청을 401로 돌렸을 때 API 호출 1회, 뒤의 두 행은 미변경이어야 한다.

### R5. P2 — 양 앱의 본인 알람 POST는 응답 유실에 대한 멱등성이 없다

- `packages/backend/src/routes/alarm-mutation.ts:258`에는 로컬 알람 ID·안정적인 요청 키 계약이 없다.
  432행에서 요청마다 새 UUID를 만들고 본인 알람 행을 INSERT한다.
- Android `AlarmSyncService.kt:82`, iOS `RemoteAlarmPushSync.swift:124`는 응답을 받은 후에야
  `remoteAlarmId`를 로컬에 저장한다.

서버 INSERT 성공 → 응답 전달 실패 → 다음 동기화의 동일 POST 순서에서는 서버에 별도 행이 생긴다.
응답을 **받은 다음**의 취소를 막는 현재 보호는 좋지만, 응답 자체를 못 받은 경우까지 해결하지 못한다.
본인 알람의 서버 중복·미아 행 문제이며, 이것만으로 로컬 알람이 두 번 울린다는 뜻은 아니다.

가족 알람은 별도의 슬롯 재사용 로직이 있으므로 본인 알람과 동일한 중복 INSERT라고 판정하지 않는다.
다만 재시도와 사용자의 의도적인 재전송을 구별하는 요청 키는 delivery version 설계에도 유용하다.

**수정 방향**: 로컬에 보존되는 operation ID를 보내고 서버에서 `(소유자, operation ID)`를
유일하게 처리한다. 같은 작업의 재시도는 같은 결과를 반환하고, 사용자의 새 변경은 새 operation ID를 쓴다.
서버 변경과 멱등 결과 기록도 원자적이어야 한다. 이 계약을 먼저 만든 뒤 batch sync를 도입한다.

**회귀 조건**: 커밋 직후 응답만 끊기, 로컬 ID 저장 실패, 프로세스 종료 후 동일 작업 재시도를 검증한다.

### R6. P2 — iOS 사용 기록은 주기 전송 경로가 연결되지 않았다

`apps/ios-native/AlarmTalk/AlarmTalkApp.swift:443`의 전경 복귀가
`UsageEventUploader.flush`의 앱 내 호출 지점이다. `BackgroundSyncTask`에는 호출이 없다.
Android는 `UsageEventUploadWorker.kt:131`에서 6시간 주기를 등록하고 앱 시작에서도 보낸다.
`docs/spec/usage-events.md` §2의 전송 계약은 앱 진입과 주기 워커다.

화면을 열지 않고 알람 해제만 하는 iOS 사용자의 기록은 백그라운드 동기화가 살아나도 올라가지 않는다.
계속 보관만 되는 것도 아니다. `UsageEventQueue.swift:51`의 2,000건 상한을 넘으면
119행에서 가장 오래된 기록부터 지운다. 상한 자체가 오류라는 뜻은 아니지만,
전송 기회가 부족하면 지연과 유실에 더 쉽게 도달한다.

**수정 방향**: 중요한 알람·접근권 정합화를 우선한 뒤, 백그라운드에 남은 시간 안에서 제한된 배치를 보낸다.
실패가 알람 동기화 성공을 뒤집지 않도록 분리하고, 취소·계정 세대·개인정보 동의를 유지한다.
OS가 매번 실행해 줄 수 있다는 보장은 두지 않는다. 울림 경로에서 네트워크를 보내는 수정은 금지다.

### Watchdog를 닫지 않는 이유

`StockClipPrefetcher.defaultVoiceProgress`는 매니페스트 파일을 읽고 JSON을 디코드한다
(`StockClipPrefetcher.swift:107`). 호출하는 `missingOrStaleCacheKeys`도 디렉터리 목록은 한 번만
읽게 됐지만, 파일이 있는 클립마다 `readMetadata`로 메타데이터를 읽는다(`AudioCacheStore.swift:600`).
`Views/Auth/StockReplacementView.swift:99`의 2초 폴링과 MainActor 호출 경로가 여전히 있다.

**152회 디렉터리 스캔을 한 번으로 줄인 것은 실제 개선**이다. 그러나 메인 스레드의 파일 읽기·
JSON 해석 비용이 0이 된 것은 아니며, 그것이 제보된 종료를 유발했다고 확정할 자료도 없다.
저장소 actor/직렬 큐의 인덱스와 다운로드 완료 이벤트 기반 진행률로 옮기는 것이 후속 방향이다.
메타데이터 누락을 곧바로 다운로드 성공으로 간주하는 식의 최적화는 하지 않는다.

완료 기준은 실기기 Time Profiler/Hangs 측정, 종료 진단 정보, 기기·빌드·설치 이력 대조다.
개발 설치 시간과 가까웠다는 이유만으로 운영 watchdog을 일괄 무시하지 않는다.

## 5. 요청·DB 묶음 처리의 권장 순서

### 먼저 할 것

1. **R2의 DB batch**: 앱→서버 HTTP는 이미 묶여 있으므로 서버→Turso 왕복부터 줄인다.
2. **같은 조회의 중복 실행 합치기**: 앱 시작·전경 복귀·탭 진입·push가 같은 세션에서 겹칠 때
   진행 중 작업을 공유한다. 키는 계정·세션 epoch·언어·권한 세대를 포함해야 한다.
   무조건 TTL로 조회를 생략해 목소리 철회·결제 강등을 늦추지 않는다.
3. **세션·권한 읽기 스냅샷 검토**: 예를 들어 iOS `SocialFeatureViewModel.swift:161` 이후는
   그룹·구독·바우처·`/auth/me`의 네 요청이다. `AlarmTalkApp.swift:270`의 plan-changed 경로는
   그 뒤 `auth.refreshUser()`도 호출한다. 읽기 전용 데이터를 한 응답으로 제공하거나 동일한
   `/auth/me` 결과를 재사용할 여지가 있다. 외부 스토어 검증·부작용 있는 결제 처리는 분리한다.
4. **요청 안의 중복 동의 조회 제거**: `middleware/consent.ts`가 읽은 값을 `/events`가 다시 읽는다.
   동일 요청에서 재사용 가능한 범위만 context로 전달한다. 동의 변경·쓰기에서는 무효화/재조회를 유지한다.
   `loadLatestConsents`는 전체 이력을 읽고 JS에서 유형별 최신 한 건을 고르므로, 이력이 커지면
   SQL에서 최신 행만 가져오는 방법을 실행계획과 함께 비교한다. 기존 인덱스가 있으므로 무작정 추가하지 않는다.
5. **R5 멱등성 후 알람 batch sync**: operation ID와 항목별 성공/실패를 정의한 뒤 작은 상한으로 묶는다.
   큰 배치 한 건의 오류가 정상 알람들까지 막지 않도록 하고, 가족 전송·삭제의 의미를 보존한다.

### 측정한 뒤 할 것

- 음성 클립 준비: 이미 병렬 다운로드와 캐시가 있다. 필요한 클립의 메타데이터 조회를 묶거나
  매니페스트에 필요한 정보를 함께 주는 것은 후보지만, 클립별 접근권·철회 확인을 생략해서는 안 된다.
  모든 오디오 바이트를 거대 JSON 응답에 넣는 방향은 피한다.
- cron: 정리·권한 정합화·외부 TTS 작업의 호출 예산과 지연을 따로 계측한다. 하나의 실행이
  예산을 소진하면 뒤의 일을 `catch`로 감싸도 예산이 복구되지는 않는다. 필요하면 작업 큐로 분리하되
  클라 알람 발사를 서버 cron에 의존시키지 않는다.
- `Promise.all`은 대기 시간을 겹칠 수 있어도 HTTP 요청 수를 줄이는 batch가 아니다.
  외부 API·DB의 병렬 한도와 동일 트랜잭션의 순서 조건을 확인하고 제한된 동시성을 쓴다.

## 6. 권장 완료 기준

### 다음 수정 순서

1. R1 매니페스트 권위·계정 경계, R3 세션 저장/메모리 수렴.
2. R2 이벤트 DB batch와 실제 운영 subrequest 설정 확인, R4 Android 전경 401 중단.
3. BGTask 실기기 검증과 Watchdog 측정. OS 콜백이 실제 실행됐다는 증거 없이 이슈를 닫지 않는다.
4. R5 생성 멱등성, R6 iOS 기록 전송 기회, 공통 fixture와 요청 중복 제거.
5. 측정 결과에 따라 읽기 스냅샷 API·작은 sync batch·음성 준비 최적화를 각각 별도 변경으로 진행한다.

### 회귀와 운영 관찰

- iOS: 백그라운드 콜드 launch, 실제 BGTask 전달, 성공 완료, 만료 취소, 오프라인, 토큰 갱신,
  계정 전환, 음성 접근 철회, 비행기모드 발사. 디버거의 `_simulateLaunchForTaskWithIdentifier`
  사용은 기기 개발 검증용이며 앱 제품 코드에 넣지 않는다.
- Android: 만료 세션으로 인증 워커 6개 및 전경 push 실행, 명시적 로그아웃 중 늦은 401,
  재로그인 뒤 밀린 작업 재개, Doze·재부팅·오프라인 발사.
- 서버: 100건 이벤트 배치, 응답 유실 재전송, 권한이 다른 항목의 혼합 요청,
  동의 철회, 시간 역전, transaction rollback, 호출 횟수 예산.
- CI: iOS launch 경계 테스트와 정적 lint는 유지한다. `.github/workflows/ios-build.yml`은
  유닛 테스트·Release 빌드를 실행하지만 UI 테스트는 실행하지 않는다. UI 변경 때의 선택 실행이나
  정기 UI suite가 필요하다. iOS 체크의 실제 필수 여부는 원격 브랜치 보호 설정에서 따로 확인한다.
- 운영: 크래시 감소만 보지 말고 BGTask 시작/완료/만료, 동기화 성공률, 이벤트 큐 최고 대기 시간·
  상한 삭제 수, API별 DB 왕복·p95 지연, 원인별 프리렌더 실패를 본다.
  토큰·문구 원문·녹음·개인 식별정보를 새 로그에 넣지 않는다.

**출시 판단**: 제보의 대규모 테스트 통과는 유용하지만, 현재 테스트가 위 경합과 OS 실행 경계를
모두 검증한다는 뜻은 아니다. 특히 R1과 BGTask 실기기 확인을 남겨 둔 채
“양 앱 모두 문제 없이 해결 완료”라고 결론내리지 않는다.

### 구현한 것

| 항목 | 수정과 회귀 방지 |

| R1 매니페스트 경합·계정 혼입 | iOS 두 writer가 저장소 전역 조회 티켓을 사용한다. 세션 토큰 CAS·소유자 포함 파일·지연 응답 무효화·메모리 캐시를 추가했다. 같은 계정 재시작은 오프라인 파일을 보존하고 계정 변경은 격리한다. 응답 역전·실패 뒤 역전·계정 교체·재시작·레거시 무소유 파일 거절을 검사했다. |

| R5 본인 알람 생성 재전송 | 두 앱이 로컬 UUID를 보내고 서버가 계정 PK와 함께 결정적 서버 ID를 만든다. 응답 유실 재전송은 **같은 ID**를 `creation_replayed = true`와 함께 돌려주되 본문은 저장된 행이 아니라 **요청의 에코**다. 앱은 `id`·`creation_replayed` 만 읽고 최신 로컬 편집을 그 ID에 PATCH한 뒤 완료로 기록한다. 가족 수신 슬롯은 바꾸지 않는다. 새 테이블/마이그레이션은 필요하지 않다. |
| R6 iOS 사용 기록 전송 | BGTask의 필수 정합화 뒤 최대 100건 한 배치만 보낸다. 실패·취소·계정 교체는 큐를 보존한다. 선택 작업의 시간 초과가 필수 작업 성공을 뒤집지 않으며 BGTask 완료 통보는 경합해도 한 번이다. |
| Watchdog 관련 반복 IO | 받기 화면·클론 준비·목소리 목록의 반복 진행률 계산과 준비도 캐시 검사를 메인 액터 밖으로 옮겼다. 매니페스트는 메모리에 재사용한다. 편집 진입의 단발성 동기 검사는 남아 있다. **원래 watchdog 원인은 여전히 미확정**이다. |
| 생성 계약 추가 결함 | 처음 동기화하는 꺼진 본인 알람은 서버에서도 `is_active=false`로 생성한다. 요청에 임의 `id`가 섞여도 실제 저장 ID를 응답한다. 실제 libSQL과 전체 마이그레이션으로 회귀 검사했다. |
| 공통 계약·CI | 이메일 정규식의 shared/Android/iOS 일치를 새 CI 검사로 강제한다. iOS의 무시된 DerivedData를 ESLint·문서 링크 검사에서 제외해 생성 산출물 때문에 검사가 실패하지 않게 했다. 제품 소스 검사 범위는 줄이지 않았다. |
| 검증에서 잡힌 것 | iOS 프리페처가 `.superseded` 를 `.failed` 로 뭉치던 것과 BG usage flush 의 취소 노이즈는 검증에서 잡혀 같은 커밋에서 고쳤다. |

### Sentry 밖에서 실기기로 발견한 결함

음력 항목은 새 발견이 아니다 — HEAD 의 `IcuLunarConverter` KDoc 이 「timeZone 고정만으로
충분하다」고 잘못 결론냈던 것을, 이번에 실기기 계측 테스트로 반증한 것이다.
A32(Android 13)의 기존 음력 계측 테스트가 **수정 전 2개 모두 실패**했다. 2028년 설날은
기대값 1월 27일 대신 1월 26일이었고 시드 밖 연도의 공휴일 판정도 실패했다. Android는
`ChineseCalendar`의 시간대만 서울로 바꾸고 있었으며 iOS는 이미 ICU `dangi`를 사용했다.
시간대 설정은 중국 역법의 천문 계산 자오선을 바꾸지 않는다는
[ICU 문서](https://unicode-org.github.io/icu-docs/apidoc/dev/icu4j/com/ibm/icu/util/ChineseCalendar.html)와
[KASI 달력자료](https://astro.kasi.re.kr/life/post/calendarData)를 대조했다.

Android도 ICU `dangi`로 바꿨으며 **동일 A32에서 2개 모두 통과**했다. 2024~2031년의
설날·추석·부처님오신날을 UTC/서울/로스앤젤레스 시간대에서 비교한 72개 벡터와 시드 밖
공휴일 판정을 포함한다. 테스트 빌드는 Sentry DSN을 비웠고 정식 앱이 아닌 dev flavor를 사용했다.
이는 공휴일 엔진의 실기기 검증이지 잠금·Doze·재부팅 중 실제 발사 전체를 검증한 것은 아니다.

### 배포 전 남은 확인

- 실제 iPhone의 OS BGTask 전달·콜드 실행·만료·성공 완료와 다음 예약. 현재 비격리 회귀
  테스트는 시스템 전달 전체를 대신하지 않는다. 이 변경으로 기기 앱을 덮어 설치하지 않았다.
- iPhone/Android의 비행기모드 목소리 발사, 재부팅/잠금/Doze, 계정 A→B 전환,
  푸시 미배달 뒤 가족 알람 수신·음성 철회. 자동 테스트는 로직을 검사하지만 실제 울림을 보증하지 않는다.
- 실제 스토어 구매/복원/보류/환불, 두 기기 동시 사용, 탈퇴·동의 철회의 운영 연동.
- Watchdog의 Time Profiler/Hangs 측정과 진단 로그. IO를 옮겼다는 것만으로 기존 이슈를 닫지 않는다.
- 배포 후 Sentry 재발 여부와 API 지연/DB 호출·큐 대기 시간 관찰. 이번 작업은 운영 Sentry/DB를
  조회하거나 서버를 배포하지 않았다. 본인 알람 생성 멱등성은 새 서버와 새 앱이 함께 적용되어야 한다.

읽기 스냅샷 API·알람 일괄 sync·프로세스 TTL 캐시는 추가하지 않았다. 이미 확인한 DB 왕복은
줄였지만 권한 철회·가족 전송 의미를 바꿀 수 있는 광범위한 묶음 처리는 측정과 별도 계약이 먼저다.
모든 운영 동작이 검증됐거나 남은 버그가 없다는 인증은 아니다.
