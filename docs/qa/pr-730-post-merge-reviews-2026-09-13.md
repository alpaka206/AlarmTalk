## #735 재후속 — 복구 요청 자체의 응답 유실

[복구 재시도 P1](https://github.com/alpaka206/AlarmTalk/pull/735#discussion_r3997319922)은
`4075c204`의 푸시 캐시 무효화에 **도달하지 못하는 경로**였다. 탈퇴 취소는 서버에서
성공했어도 응답을 못 받으면 기존 API 재시도가 `NO_PENDING_DELETION`으로 끝났고,
일반 `/auth/me` 조회도 화면만 열고 복구 후처리를 건너뛰었다.

- 서버 취소는 같은 쓰기 트랜잭션에서 pending을 복구하거나 **이미 active면 무변경 성공**으로
  수렴한다. 없는 계정은 성공시키지 않는다. 기존 오류 코드의 이름은 바꾸지 않았다.
- iOS는 네트워크/5xx/해석 실패와 구서버의 `NO_PENDING_DELETION`을 받으면 `/auth/me`로
  재확인한다. 해당 오류 자체는 성공 근거가 아니며 여전히 pending/알 수 없는 상태이거나
  재확인 실패면 상태·정리 표시를 보존한다.
- `completeAccountRecovery`를 직접 성공 응답과 일반 조회의 pending→active 전환이 공유한다.
  저장된 세션의 pending도 전환 근거로 사용해 재실행 뒤에도 푸시 무효화에 도달한다.
  해당 계정의 미완료 탈퇴 정리를 해제하고, 세션의 active를 저장하고, 복구 훅을 호출한다.
- 복구 전 읽기 응답은 `accountRecoveryRevision`으로 무효화한다. 같은 토큰의 늦은 pending
  응답이 복구를 되돌리지 못하며, 계정/토큰 변경·취소 가드도 유지한다. 이미 active인 계정을
  다시 조회한다고 복구 훅을 반복하지 않는다.

## #735 추가 — 실제 디코더 오류가 재확인 분기에서 빠짐

[응답 디코딩 P2](https://github.com/alpaka206/AlarmTalk/pull/735#discussion_r3997367548)는
`b02d0711`의 해석 실패 처리에 남은 오류 타입 누락이다. `AlarmTalkAPI.request`는 2xx 본문을
`JSONDecoder.decode`로 읽다가 실패하면 `DecodingError`를 그대로 전달한다. 앞선 수정은
`APIError.invalidResponse`만 처리했고, 해당 테스트도 그 오류를 직접 주입해 실제 경로와 달랐다.
서버는 복구됐어도 잘린 응답/잘못된 스키마를 받으면 `/auth/me` 재확인과 푸시 훅을 건너뛰었다.

- `isAmbiguousDeletionCancellation`에 `DecodingError`를 포함했다. 다른 API의 오류 계약은
  바꾸지 않고, 탈퇴 취소 뒤 재확인으로만 연결한다. 복구 확정은 기존처럼 active 조회가 필요하다.
- `AccountRecoveryDecodingTests`는 오류를 직접 주입하지 않는다. 격리한 `URLProtocol`로
  실제 API에 잘못된 200 응답을 전달해 디코딩 → 재확인 → 세션 저장·표시 해제·복구 훅을 연결한다.
  재확인이 pending/503/디코딩 실패인 경우에는 복구를 확정하지 않는 사례도 작성했다.
- 같은 종류의 후속 수정에서는 **오류를 만드는 실제 계층의 타입과 테스트 입력을 맞춘다.**
  `APIError.invalidResponse` 테스트를 JSON 디코딩 실패까지 다룬 근거로 쓰지 않는다.
  동작 규칙은 [세션 스펙](../spec/session-and-auth.md)에 구체화했다.

## #735 재전송 후속 — 생성 순번만으로는 새 전달 세대를 볼 수 없음

[재전송 커서 P1](https://github.com/alpaka206/AlarmTalk/pull/735#discussion_r3998707237)은
`252a222a`의 순번 발급이 INSERT에만 묶인 데서 생겼다. `claimTargetedAlarmSlot`이 같은 id를
재사용하고 호출자가 `delivery_version`/내용을 UPDATE하면, 앞 페이지에서 읽은 순번이 그대로라
뒤 페이지에서 새 전달을 못 봤다. 옛 ACK의 삭제 방어만으로는 새 내용의 도착을 앞당기지 못한다.

- 기존 115를 덮어쓰지 않고 마이그레이션 116을 추가했다. 타깃 행의 전달 버전이 실제 바뀌면
  같은 쓰기의 트리거가 새 AUTOINCREMENT 순번을 발급한다. 재전송뿐 아니라 다른 발신자의
  슬롯 교체로 비활성화되는 세대도 포함한다. 같은 버전 재쓰기와 일반 편집은 움직이지 않는다.
  순번 발급 실패는 새 버전/내용과 함께 롤백한다.
- iOS에서 모든 중복 id를 실패시키던 처리도 같이 고쳤다. 뒤 페이지에서 처음 보는 명시적
  전달 버전을 받으면 옛 항목을 제거하고 최신 항목 하나를 마지막 읽기 순서로 남긴다.
  기존 위치에 덮어쓰면 슬롯 교체 적용 순서가 바뀔 수 있으므로 최신 읽기 순서도 보존한다.
  같은 버전/버전 없는 중복, 이미 본 옛 세대, 한 페이지 안의 중복은 계속 거절한다.
- 재발 방지 기준: **전달 버전 발급 → 커서 전진 → 페이지 간 최신 세대 병합 → 해당 버전 ACK**를
  한 계약으로 다룬다. 새 행 INSERT만을 재전송의 대리 사례로 쓰지 않는다.
  마지막 조회가 끝난 뒤의 재전송은 여전히 새 푸시/다음 pull이 필요하다.

배포 선행 조건은 **지원 서버와 마이그레이션 116까지 완료한 뒤 iOS 배포**로 갱신했다.
이번에는 마이그레이션을 적용하거나 배포하지 않았다.

## #735 복구 저장 순서 후속 — active와 옛 탈퇴 표시가 함께 남는 창

[탈퇴 표시 순서 P2](https://github.com/alpaka206/AlarmTalk/pull/735#discussion_r3998752416)는
`a2b199ec`의 복구 완료 처리에서 active 세션을 저장한 뒤 미완료 탈퇴 표시를 지우던 순서다.
그 사이 종료되면 다음 실행의 `AlarmTalkApp`이 표시를 따라 알람을 끄고 탈퇴 정리를 이어간다.
이미 active로 저장됐으므로 일반 조회의 pending→active 복구 처리도 다시 실행되지 않는다.

- 푸시 준비 완료와 출처/취소 가드 뒤에 **본인 탈퇴 표시·정리용 토큰 해제 → active 세션
  저장/게시 → pending UI 해제 → APNs 시작** 순서로 변경했다. 다른 계정의 정리는 보존한다.
- 표시 해제 뒤 active 저장 전에 종료되면 저장된 pending 세션이 남아 다음 조회로 복구를
  다시 완료할 수 있다. 이미 적용한 푸시 영속 무효화 순서는 유지한다.
- 회귀 방지: `AuthViewModelTests`의 실제 session 게시 시점(Keychain 저장 직후)에 본인 표시와
  정리 토큰이 이미 없어야 한다고 단언한다(직접 취소/일반 조회 2경우). 완료 훅에서만 검사하면
  이 창을 놓친다. 기존 재실행 테스트도 표시 해제 직후 중단 상태를 사용하도록 강화했다.

## #737 CI 실패 복구 — 콜백의 MainActor 누락

이후 사용자가 CI는 허용하고 에이전트는 커밋·푸시 뒤 종료하라는 뜻으로 명확히 했다.
로컬 빌드는 `develop → main` 머지 완료 뒤에 다루며 CI 완료를 기다리지 않는다.

실패한 [iOS 실행 34762672468](https://github.com/alpaka206/AlarmTalk/actions/runs/34762672468)은
`7ea84109`의 `DuplicateAlarmReplacement.swift`에서 `sending 'conflict' risks causing data races`
두 건으로 컴파일이 중단됐다. 테스트는 시작하지 못했고 Release 단계도 실행되지 않았다.
`removeReplacementConflicts` 함수에만 `@MainActor`가 있고 `deleteRemote`/`deleteLocal`
콜백 타입에는 없어, generic `Conflict`를 격리 밖으로 보내는 호출로 해석된 것이다.
콜백 두 개와 같은 파일의 롤백 취소 콜백에도 `@MainActor`를 명시했다. Swift 동시성 검사나
테스트를 끄거나 CI 설정을 완화하지 않았다.

같은 워크플로의 직전 develop 실행과 직전 9회 iOS 실행은 성공했다. 확인한 이전 실패
`34696615869`는 `BillingPreflightTests`의 상태 값 비교 실패로, 이번 컴파일 오류와 원인이
다르다. 이번 HEAD의 CI 워크플로(백엔드/shared/voice·lint)는 이미 성공했다.

- 로컬 Xcode 26.6, iPhone 17/iOS 26.5 시뮬레이터, CI와 같은 한국어·ad-hoc 서명 옵션:
  전체 `AlarmTalkTests` 성공. xcresult 요약 기준 811 통과, 9 스킵, 0 실패.
- 같은 Xcode의 generic iOS 대상 Release 빌드 성공(서명 없이 CI와 같은 옵션).
- 수정 커밋 `13e02f97`의 원격 [필수 검사 7개](https://github.com/alpaka206/AlarmTalk/actions/runs/34763267125),
  [Android](https://github.com/alpaka206/AlarmTalk/actions/runs/34763267206),
  [CodeQL](https://github.com/alpaka206/AlarmTalk/actions/runs/34763267156)은 성공했다.
- 같은 커밋의 [PR iOS 실행](https://github.com/alpaka206/AlarmTalk/actions/runs/34763267138)은
  유닛 테스트가 성공한 뒤 로컬 빌드 제한을 잘못 해석해 Release 빌드 도중 취소했다. 전체 실행 성공으로
  표시하지 않는다. 먼저 시작한 중복 수동 iOS 실행 `34763123651`도 취소했다.
- develop 머지 뒤 잘못 취소한 [iOS](https://github.com/alpaka206/AlarmTalk/actions/runs/34763738173)·
  [Android](https://github.com/alpaka206/AlarmTalk/actions/runs/34763738186)는 재실행을 요청했다.
  이미 머지된 PR의 중복 실행은 재개하지 않으며, develop 실행의 완료를 기다리지 않는다.
- 수정 HEAD의 원격 상태는 [#737 체크](https://github.com/alpaka206/AlarmTalk/pull/737/checks)에서 확인한다.
- 실기기의 AlarmKit 울림·예약/취소 및 실제 푸시 전달은 자동 테스트의 검증 범위 밖이다.

## 릴리스 단계에서 남은 확인

- 향후 실행 요청 시 수정 HEAD의 네이티브 CI 확인(백엔드 로컬 실행 결과는 위 절 참조).
- Android·iOS 커서 지원 서버와 마이그레이션 116까지 선배포 확인(기존 앱의 offset API는 서버가 유지).
- 두 기기에서 페이지 조회와 앞쪽 알람 ack/삭제를 겹쳐 다음 가족 알람 도착을 확인.
- 푸시 해제의 서버 처리 후 응답만 유실시키고 복구: 같은 APNs 토큰 재등록 및 재실행 재시도 확인.
- **탈퇴 취소 성공 응답도 유실**시킨 경우: 재확인 active→강제 재등록, 재확인도 실패한 뒤
  재시도/일반 조회/재실행에서 복구 후처리 재개와 가족 알람 수신 확인.
- iOS 실기기: 탈퇴 대기로 재로그인 → 복구 → 앱 재시작 없이 다른 기기에서 보낸 가족 알람
  푸시 수신·로컬 저장·예약 확인. 알림 표시 권한 거부 시에도 background 등록 경로 확인.
- iOS 실기기: 앞쪽 소유 알람 100개 이상이 있는 계정에 가족 알람을 보내 페이지 뒤쪽
  수신·음원 확보·예약·ack 확인. 이후 비행기 모드 울림 확인(발사 경로는 변경하지 않음).

  원본 리뷰 스레드를 해결 완료로 닫지 않는다.
