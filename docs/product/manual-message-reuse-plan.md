# 직접 입력 문구 보관함 — 기획/계획서 (초안, 2026-09-06)

> **한 줄**: 한 번 만든 직접 입력 문구는 다시 만들지 않는다. 기록은 남기고, 오디오는
> **알람이 아니라 목소리**에 매달아 둔다.
>
> 상태: **미구현 · 결정 대기.** 아래 「지금 어떻게 도는가」는 코드에서 확인한 사실이고,
> 「바꾸려는 것」부터가 제안이다.

## 0. 지금 어떻게 도는가 (2026-09-06 코드 확인)

확인한 파일을 함께 적는다 — 이 문서가 낡았는지 판단할 근거다.

### 0-1. 월 한도는 **생성할 때만** 깎인다 — 같은 문구는 공짜다

- 한도: 개인 30 / 커플 50 / 가족 100, **KST 월 단위**, 커플·가족은 그룹이 한 풀을
  나눠 쓴다 (`packages/backend/src/lib/manual-tts-quota.ts`).
- `POST /tts/generate` 는 **캐시를 먼저 찾고**, 못 찾았을 때만 `reserveManualTtsQuota`
  로 카운터를 올린다 (`packages/backend/src/routes/tts.ts`). 생성이 실패하면 환불한다.
- 즉 **같은 문구 = 차감 없음**이 이미 규칙이다. 단 '같다' 의 기준은 캐시 키다:
  제공자 · 제공자 보이스 id · 목소리 프로필 id · 모델 · 언어 · **정규화한 문구** · 출력
  포맷 (`packages/backend/src/lib/audio-cache.ts` 의 `computeTtsCacheKey`).
  → 같은 문구라도 **목소리를 바꾸면 새 생성**이다(그게 맞다 — 다른 소리를 만드는 것이니).
- 직접 입력은 **사용자끼리 캐시를 공유하지 않는다**(`anyUser: isSystemVoice &&
  !isManualGeneration`). 공유하면 남의 `messages` 행을 물어 저장이 404 로 막히고,
  한도도 안 깎이는 구멍이 된다.
- 앱은 대개 서버까지 가지도 않는다. 같은 기기에서 같은 문구를 다시 치면 로컬 입력 캐시
  (`AlarmAudioStore.ttsInputKey` + `linkTtsInput`)가 파일을 그대로 돌려준다.

### 0-2. 보관함 테이블은 **이미 있다**

- `message_library(id, user_id, message_id, is_favorite, received_at)` — 초안 미리듣기가
  아닌 모든 생성이 여기에 한 줄을 남긴다(`routes/tts.ts`).
- `GET /tts/messages` 가 그 목록을 준다(목소리·카테고리 필터, 페이지네이션, 프리셋·삭제된
  목소리 제외).
- ⚠ **두 앱 어디에서도 이 목록을 쓰지 않는다.** 앱이 부르는 건 개별 오디오
  (`GET /tts/messages/:id/audio`) 뿐이다. 즉 **데이터는 쌓이는데 보여 주는 화면이 없다.**

### 0-3. 오디오는 30일이면 사라진다

`packages/backend/src/lib/audio-retention.ts` (`cleanupExpiredAudio`):

- `generated_audio_assets` 는 **생성 30일** 뒤 정리 대상이다. 지울 때 R2 오브젝트를
  삭제 큐에 넣고 `messages.audio_url` 을 비운다.
- 예외 둘: **알람이 그 메시지를 참조 중**이거나, **프리셋(`is_preset=1`)** 이면 건너뛴다.
- 기준이 `created_at` 이라, 알람에서 떼어 낸 문구는 **아무리 자주 써도** 만든 지 30일이면
  사라진다.

### 0-4. **지우는 문은 이미 목소리 축이다** — 동의 철회·해지도 그 길로 간다

- 동의 철회(`user.ts` → `deleteSensitiveVoiceDataForUser`)는 **내가 등록한 클론 프로필**을
  축으로 지운다: 그 목소리의 `generated_audio_assets`·`message_library`·`messages`·
  `voice_uploads`·`voice_profiles` + R2·ElevenLabs 삭제 큐.
  ⚠ 예전에는 `user_id` 축도 함께 걸려 있어 **시스템 목소리로 만든 문구까지** 지웠고, 그건
  고쳐졌다(같은 파일 주석).
- 요금제 해지는 **즉시 삭제가 아니다.** 무료로 내려갈 때는 제공자 클론만 반납하고
  (`evicted_*` 표식) 데이터는 유예 동안 남는다 — 그 사이 재구독하면 재클론으로 돌아온다.
  유예가 지나면 `sweepPaidVoiceRetention` 이 같은 `deleteSensitiveVoiceDataForUser` 를 부른다.
- 탈퇴는 `purgeUserAccount` 가 계정 전체를 지운다.

→ 즉 **"목소리 삭제 → 오디오 삭제" 는 이미 서버의 구조**다. 새로 만들 것이 아니라
**문서로 고정하고, 알람 삭제 쪽만 떼어내면 된다**(아래 0-5).

### 0-5. 알람을 지우면 **오디오도 지워진다**(로컬)

- 안드로이드: `AlarmRepository.deleteAlarm` → `deleteCachedAudioIfUnreferenced`
  (같은 캐시 키를 쓰는 다른 알람이 없으면 파일 삭제).
- iOS: `AlarmKitViewModel.deleteLocalAlarm` → `store.delete(record)` 가 돌려준 캐시 키를
  `AudioCacheStore.deleteCachedAudio` 로 삭제.
- 목소리를 지우거나 유료가 끊기면 서버도 그 목소리의 `messages`·`message_library`·
  `generated_audio_assets` 를 지우고 R2 삭제를 큐에 넣는다
  (`packages/backend/src/lib/paid-voice-cleanup.ts`).

**정리**: "같은 문구면 공짜" 는 **이미 맞고**, 문제는 그 사실이 **보이지 않고 오래 못 간다**는
것이다. 30일 TTL 과 알람 삭제 시 로컬 삭제가 재사용의 두 구멍이다.

## 1. 바꾸려는 것 (2026-09-06 결정)

1. **보관함을 화면으로 꺼낸다.** 직접 입력 화면에서 이전에 쓴 문구를 고를 수 있게 한다.
2. **오디오 수명은 목소리에 매단다.** 알람을 지워도 오디오는 남는다. **목소리가 살아 있는
   동안은 계속 보관한다 — 기간·개수 상한을 두지 않는다.**
   - 이유는 비용 절감이 아니라 **경험의 동일성**이다. 재합성은 같은 문구라도 소리가 미묘하게
     달라진다. 오래 쓴 알람이 어느 날 다른 억양으로 울리지 않게 하려면 그때 만든 바이트를
     그대로 들고 있어야 한다.
3. **DB 기록은 스토리지보다 오래 산다.** 어떤 이유로 오디오 바이트가 사라져도
   `messages`·`message_library` 행은 남는다(그 문구를 다시 만들 때 근거가 된다).
   행까지 사라지는 경우는 **목소리가 사라질 때** 하나뿐이다(아래 4).
4. **지우는 문은 하나다 — 목소리 삭제.** 동의 철회·요금제 해지·탈퇴는 **목소리를 지우고**,
   목소리 삭제가 그 목소리의 오디오·문구·보관함 행을 지운다.
5. **한도는 '새로 만드는 횟수'다.** 오디오가 남아 있어 재합성을 안 하더라도, **새 알람에
   문구를 새로 붙이면 1회 차감**한다(아래 §3-1).

## 2. 데이터 모델 (append-only)

`message_library` 에 **컬럼 하나**만 더한다. 테이블을 새로 만들지 않는다 — 이미 모든
생성이 여기 한 줄을 남기고 있어 이력이 이어진다.

| 컬럼 | 뜻 |
| --- | --- |
| `last_used_at` | 알람에 붙은 마지막 시각. 목록 정렬과 '언제 썼는지' 표시 |
| `alarm_count` | 이 문구로 만든 알람 수(선택, 목록 맥락용) |

**활성/비활성 상태 컬럼은 두지 않는다.** 보관 상한을 없앴으므로 상태가 갈릴 일이 없다 —
목소리가 있으면 문구도 오디오도 있고, 목소리가 없으면 셋 다 없다. (앞선 초안에서 제안한
'오디오 유무로 유도' 도 이제 불필요하다. 그 판정은 **차감**과 무관하고 — 차감은 §3-1 대로
'새로 만들었는가' 로 정한다 — 우리 쪽 재합성 여부를 가르는 내부 사정일 뿐이다.)

- 마이그레이션은 **제자리 추가**뿐이다(CLAUDE.md 「prod DB 전체 초기화는 하지 않는다」).
  `last_used_at` 은 `received_at` 으로 백필한다.
- 새 컬럼을 읽는 경로는 **fail-closed** 로 둔다(배포가 마이그레이션보다 먼저 도는 창).

## 3. 규칙

### 3-1. 차감 — **새로 만들 때마다** 1회

한도는 "이 달에 직접 입력 문구를 **몇 개 새로 만들 수 있는가**" 다. 우리가 실제로
합성했는지(=캐시가 살아 있었는지)는 **사용자에게 보이지 않는 사정**이므로 계산에 넣지
않는다. 오디오가 남아 있으면 우리는 비용을 아끼고 사용자는 같은 소리를 즉시 얻는다 —
그 이득은 속도와 **소리의 동일성**으로 돌려주고, 횟수는 그대로 센다.

| 상황 | 차감 |
| --- | --- |
| 새 문구를 쳐서 알람에 붙인다 | **1회** |
| 예전에 쓴 문구를 **새 알람**에 다시 붙인다(보관함에서 고르든 다시 치든) | **1회** |
| 이미 그 문구를 쓰는 알람을 **문구 변경 없이** 다시 저장한다 | 없음 |
| 알람의 문구를 A → B 로 바꾼다 | **1회**(B 를 새로 붙였다) |
| 같은 문구를 **다른 목소리**로 붙인다 | **1회** |

판정의 단일 기준: **알람에 직접 입력 문구가 새로 붙는 순간**. 열어서 보기만 하거나,
문구를 안 바꾸고 시간만 고쳐 저장하는 것은 차감이 아니다.

⚠ **이 규칙은 지금 동작과 다르고, 지금 문서와도 충돌한다.** 셋을 같이 고쳐야 한다:
1. **서버가 그 순간을 볼 수 있어야 한다.** 지금은 캐시 히트면 `reserveManualTtsQuota` 를
   건너뛴다. '붙이는 행위' 를 세려면 알람 저장 경로(또는 전용 엔드포인트)에서 카운트해야
   한다 — 합성 여부와 분리한다.
2. **앱이 서버를 안 부르는 길이 있다.** 같은 기기·같은 문구는 로컬 캐시가 히트해 서버까지
   가지 않는다. 차감하려면 저장할 때 반드시 한 번은 서버에 알려야 한다.
3. **오프라인 약속을 다시 정해야 한다.** CLAUDE.md 「직접 입력은 문구까지 기억한다」 절은
   지금 *"글자가 같으면 서버 호출도 월 한도 차감도 없이 곧바로 저장된다(오프라인 포함)"*
   고 적고 있다. 새 규칙에서는 오프라인 저장분을 **나중에 동기화할 때 차감**하거나,
   오프라인 재사용만 예외로 두거나 — 둘 중 하나를 골라 그 절을 고쳐야 한다.

### 3-2. 수명

| 대상 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 서버 오디오(R2) | 생성 30일 (알람 참조·프리셋 제외) | **그 목소리가 살아 있는 동안 계속 보관.** 기간·개수 상한 없음 |
| 서버 DB 행(`messages`·`message_library`) | 오디오와 함께 정리되기도 한다 | **오디오가 사라져도 남는다.** 목소리가 사라질 때만 지운다 |
| 로컬 오디오 | 알람 삭제 시 함께 삭제 | **알람 삭제로는 안 지운다.** 목소리 삭제 때만 |
| 지우는 문 | 여러 갈래(알람 삭제·TTL·목소리 삭제·철회·해지) | **목소리 삭제 하나.** 동의 철회·요금제 해지·탈퇴는 목소리를 지우고, 그 뒤는 같은 경로 |

⚠ **상한을 없앤 대가는 저장 비용이다.** 유료 사용자 1인이 한 달 한도를 다 쓰면 문구
30~100개, 문장 하나가 수십 KB 수준이라 개인 단위로는 작다. 다만 **삭제되지 않는 한 계속
쌓이므로**, 총량 모니터링(사용자당 오브젝트 수·바이트)은 붙여 두는 것이 좋다. 상한을 다시
두게 되면 그때는 이 표부터 고친다.

### 3-3. 화면

- 직접 입력 다이얼로그 아래 **'이전에 쓴 문구'** 목록(최근순, 그 목소리 것만).
  - 고르면 즉시 적용된다(기다림 없음 — 오디오가 이미 있다).
  - 다만 **새 알람에 붙이는 것이면 1회 차감**이므로, 목록 위에 남은 횟수를 함께 보여
    준다("이번 달 27/30 남음"). 고르는 순간이 아니라 **저장할 때** 깎인다.
- 목록에서 **지우기**를 준다. 사용자가 지운 것은 기록까지 없앤다 — 「기록은 남긴다」는
  **시스템이 정리할 때**의 규칙이지, 사용자의 삭제까지 막는 규칙이 아니다.
- 목소리를 지우면 그 목소리의 목록도 함께 사라진다(§3-2 의 '지우는 문' 하나).

## 4. 구현 순서

1. **서버 — 보관**: `cleanupExpiredAudio` 의 TTS 정리에서 **직접 입력 메시지를 제외**한다
   (목소리가 살아 있으면 보관). 프리셋 예외는 그대로. 지금 로직이 `messages.audio_url` 을
   비우고 자산 행을 지우므로, 여기만 고치면 §3-2 의 보관 규칙이 선다.
2. **서버 — 기록**: `message_library.last_used_at` 추가 + 백필, `GET /tts/messages` 응답에
   싣는다. 목소리 삭제 경로(`deleteSensitiveVoiceDataForUser`·`deletePaidVoiceDataForUser`)는
   **이미 목소리 축으로 지운다** — 손댈 곳이 없다.
3. **서버 — 차감**: '문구를 알람에 새로 붙였다' 를 세는 자리를 만든다(알람 생성·수정
   경로에서 직접 입력 문구가 새로 붙었을 때). 합성 여부와 분리하고, 캐시 히트에도 센다.
   기존 `reserveManualTtsQuota` 는 그대로 두되 **호출 지점을 옮기는 셈**이다.
4. **앱(양쪽) — 삭제**: 알람 삭제 시 오디오를 지우지 않게 한다
   (`deleteCachedAudioIfUnreferenced` 호출 제거). 목소리 삭제 경로에서만 지운다.
5. **앱(양쪽) — 화면**: 직접 입력 화면에 보관함 목록(`GET /tts/messages`).
6. **문서**: `docs/spec/voice-and-message.md` 에 차감·수명 규칙을 옮기고, CLAUDE.md 의
   「직접 입력은 문구까지 기억한다」 절에서 **"차감 없이 저장된다"** 문장을 새 규칙으로
   고친다(§3-1 의 ⚠ 3번).

## 5. 정해야 하는 것

1. **오프라인 저장의 차감**(§3-1 ⚠ 3). 나중에 동기화할 때 깎을 것인가, 오프라인은
   예외로 둘 것인가. 예외로 두면 "비행기모드에서 만들면 공짜" 가 되고, 나중에 깎으면
   **이미 만든 알람이 한도 초과로 거절되는** 상태를 어떻게 보여 줄지 정해야 한다.
2. **공유 목소리의 보관함.** 지금은 캐시부터 사용자별로 분리돼 있어 남의 문구가 보이지
   않는다. 커플·가족이 같은 목소리를 쓸 때 서로의 문구를 보여 줄 것인가(문구는 개인적인
   글이라 기본은 '안 보여 준다' 가 맞다고 본다).
3. **저장 총량 감시.** 상한을 없앴으므로 사용자당 오브젝트 수·바이트를 재는 계측을
   붙일지. 늘어나는 속도를 보고 나중에 상한을 다시 논의할 근거가 된다.
