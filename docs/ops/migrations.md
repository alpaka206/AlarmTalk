# 마이그레이션 — 상태와 스쿼시 판단

## 지금 상태 (2026-08-08 실측)

| | 적용된 마지막 id | 비고 |
| --- | --- | --- |
| prod | **93** | 94–97(애플 신원·결제·푸시 복구)이 아직 안 올라갔다 — iOS 브랜치 미머지 |
| dev | **97** | |
| 코드 | **98** | 98 은 어느 DB 에도 아직 없다 |

⚠ **환경마다 다르다.** "코드에 있으니 DB 에도 있겠지" 로 판단하면 안 된다. 확인은
`_migrations` 테이블을 직접 읽는다.

## 스키마 정합성 — 확인됨

마이그레이션 전체를 빈 DB 에 처음부터 돌린 결과를 prod 스키마와 대조했다(2026-08-08):

- **테이블 일치**(29개), **뷰 일치**, 실행 중 무시 못 할 실패 **0건**
- 인덱스 차이 3개(`idx_users_apple_id`, `idx_subscriptions_apple_*`)는 **94–97 미적용
  탓**이지 결함이 아니다. 그 마이그레이션이 올라가면 사라진다.

즉 **새 환경을 만들어도 prod 와 같은 스키마가 나온다.**

## 스쿼시(1번부터 재시작)는 지금 하지 않는다

마이그레이션 파일이 2,000줄을 넘고 만들었다 지운 테이블이 여럿이라 합치고 싶은 유혹이
있다. 하지만 **지금 하면 데이터가 틀어진다.**

이유:

1. **미적용 마이그레이션이 데이터를 고친다.** 98 은 스키마가 아니라
   `UPDATE users SET family_alarm_quiet_windows = '[]'` 다. 1..98 을 id=1 로 합치면
   prod(1 이 이미 적용됨)는 그 UPDATE 를 **영영 건너뛴다** — 기존 계정의 방해금지 시간이
   그대로 남는다.
2. **환경이 서로 다른 지점에 있다.** prod 93 / dev 97. 어느 한쪽을 기준으로 합치면
   다른 쪽이 빈다.

### 언제 하면 되나

세 조건이 다 맞을 때:

1. prod·dev **둘 다 코드의 마지막 id 까지 적용**돼 있다(위 표가 모두 같은 숫자).
2. 합칠 구간에 **데이터 마이그레이션(UPDATE/INSERT)이 없다** — 있으면 그것만 베이스라인
   뒤로 남긴다.
3. 베이스라인을 **prod 의 실제 스키마에서 뽑는다**(손으로 쓰지 않는다). 그래야 새 환경이
   조용히 갈라지지 않는다.

그리고 베이스라인의 id 는 **기존 DB 가 이미 지난 번호**여야 한다(예: 1). 그래야 기존
DB 는 건너뛰고 새 DB 만 실행한다.

## 확인 방법

```
# 적용 상태
node --experimental-strip-types scripts/db-inventory.ts --env-file .dev.vars.prod
```

`_migrations` 를 직접 읽는 일회성 스크립트가 필요하면 `scripts/` 에 만들어 쓰고 지운다 —
자격증명을 쓰므로 커밋하지 않는다.
